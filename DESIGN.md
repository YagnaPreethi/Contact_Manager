
# Day 1 — OOP and Domain Modelling

## Project: Contact Manager

### Contact class
The Contact class represents one contact in the application.
It owns the contact's name, phone number, email, unique ID,
and creation timestamp.

### Why this class exists
Previously, contacts were represented as dictionaries, while
contact-related operations were implemented as separate functions.
The Contact model groups contact data and its update behaviour
into one clearly defined domain object.

### Attributes
- name: Required contact name.
- phone: Required phone number.
- email: Required email address.
- contact_id: Unique identifier generated by default.
- created_at: UTC timestamp generated when the object is created.

### Methods
- __post_init__: Normalizes and validates required fields.
- update: Validates and updates contact details.
- __eq__: Compares contacts using their IDs.
- __hash__: Hashes contacts using their IDs.

### Design decisions
- Dataclasses reduce repetitive initialization code.
- Type hints make interfaces easier to understand.
- Validation prevents missing required contact details.
- UUIDs provide stable identifiers by default.
- UTC timestamps provide consistent creation times.
- The model does not depend on the menu, terminal, or JSON file.

### Responsibilities outside the model
The application handles menu input and output.
The persistence functions load and save contacts.
The domain model owns contact-related data and validation.

### Future improvements
Integrate Contact with JSON persistence, add duplicate-contact
validation at the model/service boundary, and expand test coverage.
